## Resolved this session (for the record)

- **H4b — Free scripted database backups working end-to-end** (2026-08-08) — Supabase's Free plan runs zero automated backups; `.github/workflows/backup.yml` (added 2026-08-07) is the substitute, but the first real run failed: GitHub Actions runners have no IPv6 route, and Supabase's "Direct connection" only resolves over IPv6 without paying for the IPv4 add-on. Fixed by switching `SUPABASE_DB_URL` to Supabase's **Session pooler** connection string instead (free, IPv4). A second failure (`database "postgres\n" does not exist`) turned out to be a trailing newline pasted into the GitHub secret value along with the connection string — fixed by re-entering it as a single clean line. Confirmed working: manual `workflow_dispatch` run finished green (35s) and produced a downloadable encrypted artifact. [BACKUPS.md](BACKUPS.md) and the workflow's own comments updated to document the pooler requirement so this doesn't get rediscovered the hard way again.
- **H2 — TOTP two-factor authentication added** (2026-08-07) — self-service opt-in via App Settings (enroll with QR + secret, verify with a 6-digit code before activating, disable), using Supabase's built-in `auth.mfa` API. Both entry points that create a fresh session — password sign-in and password-reset recovery — now require the second factor via a new challenge screen whenever the account has one enrolled; gating recovery too was deliberate, since skipping it there would let anyone with access to the account's email bypass MFA entirely via a reset link. Verified live end-to-end by the user: enrollment (QR scan + code) and the sign-in challenge screen both confirmed working on the real account. No behavior change for existing accounts with no factor enrolled. Known limitation: this is enforced client-side, not via RLS `aal` checks — an already-open session on another device that predates enrollment keeps whatever access it had rather than being retroactively challenged. "Admin-specific account protections" (the other half of the original H2 wording) doesn't have a concrete equivalent in this app's data model — there's no elevated admin role beyond household membership — so nothing further was built for that part.
- **Install-banner crash on every page load** (2026-08-07, found while testing H2 live) — an IIFE ran synchronously mid-parse and called `getElementById` for `#btn-install`/`#android-section`/`#ios-steps` before that markup (later in the document) existed, throwing on literally every load. Predates this session; Sentry (added this session) caught it within minutes of going live. Fixed by deferring to `DOMContentLoaded`. Verified locally: error gone, only the expected/harmless OneSignal origin-restriction message remains on localhost.
- **H4 — Sentry error monitoring added** (2026-08-07) — client (`index.html`) and all 4 Netlify functions (via new `netlify/functions/_shared/sentry.js`) now report errors to Sentry. PII scrubbing verified twice: once locally against the real DSN (confirmed a deliberately-included sensitive string never left the browser, only an allowlisted `code` field did — visible in the Sentry dashboard's "Additional Data" section), and once live against production (`window.Sentry` active with the correct DSN host). Only static labels, HTTP/Postgrest `.code`/`.status`, and Error name+stack are ever sent — medication names/doses/photos and other free-text error detail (e.g. a Postgres constraint message that quotes a value) are dropped before anything leaves the device/server. Discovered along the way: two commits (`a8fe290`, `1d45a88`) had been pushed directly to GitHub outside this session — a real feature (Twice weekly/Monthly medication frequency support) plus the matching service-worker cache bump — confirmed with the user and merged in rather than overwritten. Backup-failure alerting specifically is still open (see H4b above).
- **H5 — Supabase service-role key rotated** (2026-08-07) — git history contained removed debug-endpoint output with partial (non-exploitable) service-role key metadata; rotated the key as a precaution. New key generated in Supabase (Settings → API), updated in Netlify across all 4 relevant deploy contexts (Production, Deploy Previews, Branch deploys, Preview Server & Agent Runners), and a fresh deploy triggered so live Functions pick up the new value. Verified via the deploy log ("Site is live"). Local development (Netlify CLI) context left unset — not used for local dev testing currently; fill in if that changes.
- **Dose history pagination** — every app load fetched a household's entire dose history forever, unbounded. Confirmed nothing needs more than the Report tab's 90-day max range, then limited the fetch to the last 120 days plus added a composite index (migration 0015) so it's fast at scale. **Needs migration 0015 run in Supabase.** Verified against the live database and a full reload.
- **Over-the-counter (OTC) medication support** — requested 2026-08-06. Manual entry already worked (pharmacy/refills are optional fields, "As needed" frequency already existed) — no changes needed there. Fixed the real gap: the Scan prompt was written entirely around pharmacy labels and the UI said "prescription label" everywhere, which would discourage anyone from trying to scan a Tylenol bottle or vitamin. Prompt now explicitly handles OTC "Drug Facts" panel format and common as-needed OTC phrasing; UI copy updated in three places to say "prescription or over-the-counter." Not tested end-to-end against a real scan (would need a live Anthropic API call) — verified the prompt is well-formed and the UI renders correctly.
- **Silent write failures on offline/network errors** — real reliability gap found while investigating "offline behavior unverified": every write in the app went through `cloudUpsert`/`cloudDelete`, which swallowed failures to a console.warn only. A dose marked "taken" while offline looked successful with no indication it never reached the cloud. Fixed: real toast on every write failure, plus a proactive online/offline banner. Verified in the browser with real dispatched events and a forced failure.
- **Accessibility (labeling + contrast + touch targets)** — every icon-only button and previously-unlabeled input now has an `aria-label`, verified via the browser's actual accessibility tree. Computed real WCAG contrast ratios for the full color palette and fixed 4 failing text colors (approved by the user first, since unlike labeling this changes visible colors). Checked all explicit button/interactive-element sizes against WCAG 2.2 SC 2.5.8 (24×24px minimum) — found and fixed one real failure (the remove-person/pet × button was 16×16px); the other small controls (confirm/cancel ✓/× at 24×24px) sit right at the floor, technically compliant. Real screen-reader testing is still a separate, unstarted piece — needs actual assistive-tech testing, not something verifiable from code.
- **Data export** — "Export My Data" in App Settings downloads a single JSON file with everything in the household (medications, dose history, family members, emergency profiles, document details). Requested in the original spec, never built until now. Verified in the browser: payload structure and the actual download mechanism.
- **H7** — Added self-service "Forgot password?" flow: sign-in form now has a working reset-request link, plus a "set new password" screen that appears automatically when a reset-email link is clicked (via Supabase's `PASSWORD_RECOVERY` auth event). Verified in the browser: toggle wiring, the real `resetPasswordForEmail` API call, loading/error/success states, the recovery screen, and both client-side validation branches.
- **Live production bug (unlabeled, found 2026-08-06)** — real user account (`ccragsdale@gmail.com`, the app owner's own daily-use account) had a valid login but no `household_members` row at all — meaning it had silently been running on local-only cached data the entire time, with invites failing and no way to tell why. Root cause traced live: `init()` falls back to a local flag and renders the app even when there's truly no session or household, with no visible indication anything was wrong. Fixed by: (1) adding the `cloudSyncMissing` banner + reachable sign-in path (see below), (2) creating the missing household for this account via the existing `create_household_with_owner` RPC, verified end-to-end (invite code generation confirmed working on the actual phone this account uses daily).
- **Supabase Auth "Site URL" was misconfigured to `localhost:3000`** instead of `https://scriptschedule.app` — discovered because a magic-link sign-in email redirected to an unreachable local address instead of the real site. This would have broken password reset, magic link, and email confirmation for every real user, not just this one case. Fixed by updating Authentication → URL Configuration → Site URL in the Supabase dashboard.
- **No path back to sign-in once a session goes missing** — `index.html` now sets `state.cloudSyncMissing` and shows a persistent banner with a working "Sign In" button (reopens the existing beta-gate sign-in form) whenever `loadHouseholdDataFromSupabase()` confirms there's truly no session, instead of silently rendering stale local data forever.
- **No visibility into which account is signed in** — App Settings now shows "Signed in as [email]" (or a "Not signed in" fallback), sourced from the same session check.
- **H1** — Dose corrections now generate an automatic, tamper-proof audit-trail entry (new `dose_event_corrections` table + trigger, migration 0014) — no client code changes needed since corrections were already real Postgres UPDATEs. **Needs the migration run in Supabase before it's live** (not yet executed against a database — no local Postgres available to test-run it directly).
- **C3** — Push reminders were scheduled using server (UTC) time with no timezone handling — fixed in `netlify/functions/schedule-push.js` using `Intl`-based timezone conversion; client now sends its IANA timezone. Verified via direct unit tests across multiple zones and both 2026 US DST transition dates. Rollout caveat: already-scheduled notifications from before this fix self-correct the next time each device opens the app (which now cancels-then-reschedules), not instantly for everyone.
- **C2 / H6** — Old, pre-XSS-fix duplicate app copies, the abandoned React scaffold (`scriptschedule/`), and ~12MB of duplicated marketing images all removed from the repo in one pass (`3fe27f2`) and confirmed gone from production (`scriptschedule.app/app-index.html` etc. now correctly serve the current patched app, 210,296 bytes, verified 2026-08-04 via direct fetch after a brief CDN propagation delay).
- Stored XSS across `index.html` — fixed, `escapeHtml()` added at 85 interpolation points.
- All four Netlify functions had zero identity checks — fixed, each now requires a verified Supabase session + per-user rate limiting.
- Misleading privacy copy ("not even us", "no one else, ever") — corrected to accurately describe household-level access control.
- Added self-service account/data deletion, verified end-to-end.
- Added "Sign Out of Other Devices," verified against the live Supabase backend.
